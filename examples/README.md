# Grit examples

Two kinds of thing live here, and the difference matters.

**[`commerce/`](commerce) and [`library/`](library) are applications.** Real
code, generated by Grit and checked in, with `go build`, `go vet` and `go test`
run against them on every push to this repository. Clone the repo and read them,
or run them. They are the only artifacts here that can prove a claim about
generated code wrong, and building `commerce` found seven framework bugs across
four releases.

**The six `job-portal-*` folders are guides.** Each is the exact sequence of
commands that builds the same Job Portal in a different Grit architecture, with
the decisions explained and the shape of the result described. They are not
repositories you clone and run.

That split is deliberate. Six checked-in copies of the same application would be
six copies to keep green against a framework that releases most days, and the
day they fell behind they would teach the wrong thing while looking
authoritative. One is affordable, and one is enough: it is a real application, so
a template change that breaks real applications fails in CI here. The guides stay
correct a different way, because the commands in them are checked against the
real command tree on every push and a renamed flag fails the docs build.

## The applications

| Folder | Architecture | What it is |
|---|---|---|
| [`commerce`](commerce) | `--triple --next` | A shop: twelve products, a Colour x Size variant matrix, a server-side basket and an admin to run it from. Modelled on vercel/commerce, with the backend that one leaves to Shopify. Its [TUTORIAL.md](commerce/TUTORIAL.md) builds the whole thing from an empty directory. |
| [`library`](library) | `--triple --next` | Authors, books and loans. Three generated resources, one hand-written policy rule, and the tests that prove the rule holds. |

`library` is the smaller read: three resources and one rule. `commerce` is the
one to read if you want to see where a generated project stops and your own code
starts, because 25 of its 821 files are hand-written and they are all the shop.

## The six shapes

| Folder | Architecture | What it is |
|---|---|---|
| [`job-portal-api-only`](job-portal-api-only) | `--api` | A Go API and nothing else. Bring your own frontend. |
| [`job-portal-single-vite`](job-portal-single-vite) | `--single --vite` | One Go binary serving a TanStack Router SPA. |
| [`job-portal-double-vite`](job-portal-double-vite) | `--double --vite` | API plus one Vite frontend with the admin inside it. |
| [`job-portal-triple-vite`](job-portal-triple-vite) | `--triple --vite` | API, public TanStack site, separate TanStack admin. |
| [`job-portal-triple-next`](job-portal-triple-next) | `--triple --next` | API, public Next.js site, separate Next.js admin. |
| [`job-portal-mobile-expo`](job-portal-mobile-expo) | `--triple --next --mobile` | The above plus an Expo app sharing the types. |

Each folder has:

- `README.md` — the architecture, and who should pick it
- `GUIDE.md` — the commands in order, from `grit new` to a running app
- `.env.example` — the environment the guide assumes
- `docker-compose.prod.yml` — how that shape deploys

## Features the guides build

The same application each time, so the only variable is the architecture:

- Auth: email and password, OAuth (Google, GitHub), JWT, TOTP 2FA
- Resources: Job, Company, Application, Category
- A dashboard with stat cards
- Data tables with sorting, filtering, pagination and export
- File uploads through presigned URLs (company logos, résumés)
- A generated admin panel with roles and permissions

## Start here

To read code, open [`library`](library) for the small version or
[`commerce`](commerce) for the real one. To build a shop yourself, follow
[`commerce/TUTORIAL.md`](commerce/TUTORIAL.md).

To build one, read the shape you want and follow its `GUIDE.md`, or let the CLI
ask you, which is the same decision with fewer tabs open:

```bash
grit new job-portal
```
