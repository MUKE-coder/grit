# Library — the checked-in reference application

A small lending library: authors, books, and the loans that connect a book to
the person who has it. Generated by Grit, checked in, and built and tested by
this repository's CI on every push.

**This is code, not a guide.** The six `job-portal-*` folders beside it are
guides: the commands that build an application, with the decisions explained.
This folder is the application. Clone the repo, open it, read it.

## Why one of these is checked in when six guides are not

A guide cannot be wrong in a way anyone notices. It describes commands, and if a
command's behaviour changes the guide goes quietly out of date while still
reading as authoritative.

This cannot. `go build ./...`, `go vet ./...` and `go test ./...` run against it
on every push to the framework, so a change to a template or a library that
breaks a real application fails here before it reaches anybody. That is the
whole reason to pay the cost of keeping an application current: it is the only
artifact in the repository that can prove a claim about generated code wrong.

It stays at the version it was generated at until somebody runs `grit upgrade`
on it, and that is deliberate too. Between upgrades it answers a question the
fresh-scaffold CI cannot: *does an application generated three months ago still
build against today's libraries?* That is the question every existing user has.

## What it was built with

```bash
grit new library --triple --next

grit generate resource Author \
  --fields "name:string,bio:text,website:url"

grit generate resource Book \
  --fields "title:string,isbn:string,summary:richtext,published:date,price:money,cover:file:image,genre:select:fiction=Fiction|history=History|science=Science,author:belongs_to:Author"

grit generate resource Loan \
  --fields "book:belongs_to:Book,borrower:belongs_to:User,borrowed_at:datetime,due_at:datetime,returned_at:datetime,status:select:out=On loan|returned=Returned|overdue=Overdue" \
  --owned-by borrower
```

Everything else in this folder came from those four commands, except one file,
which is the interesting part.

## The one hand-written file

[`apps/api/internal/policies/loan.go`](apps/api/internal/policies/loan.go) is
the worked example the generated policy stubs point at. It says that a loan
which has been returned is history: it cannot be edited, and it cannot be
deleted.

Neither of Grit's other two authorization layers can express that rule. The
permission catalogue decides whether somebody may touch loans at all, and a
librarian holding every permission still should not be able to quietly change
the dates on a closed loan. `--owned-by` decides whether a row belongs to the
caller, and the borrower does own it. The rule is about the state of the record,
which is what a policy is for.

[`apps/api/internal/handlers/loan_policy_test.go`](apps/api/internal/handlers/loan_policy_test.go)
makes the requests and checks the answers, because a claim that a returned loan
cannot be edited is either true of the running code or it is marketing.

## Running it

```bash
cd examples/library
cp .env.example .env
docker compose up -d          # Postgres, Redis, MinIO, Mailhog
grit migrate
grit seed
pnpm install
pnpm dev
```

The API is on :8080, the public site on :3000, the admin on :3001. Sign in to
the admin with the credentials `grit seed` prints.

Without Docker, set `DB_PROVIDER=sqlite` and `DB_DSN=./dev.db` in `.env`, leave
`REDIS_URL` empty and set `MAIL_MAILER=log`. The health page at
`/system/health` will show caching, jobs and cron as **off** rather than broken,
which is the point of that screen.

## What to look at

| Where | Why |
|---|---|
| `apps/api/internal/policies/loan.go` | The rule, and the only file here that was written by hand |
| `apps/api/internal/access/registry.go` | What every route demands of a caller, generated from `routes.go` |
| `apps/api/internal/routes/loan_routes.go` | A resource owns its routes; delete the file, delete the resource |
| `apps/api/internal/factory/` | Valid records for tests, one builder per resource |
| `apps/api/internal/testkit/` | The shared database, request client and assertions |
| `apps/admin/resources/` | The admin screens, declared rather than written |
| `packages/shared/` | The Zod schemas and TypeScript types, generated from the Go models |

## Running the tests the way CI does

```bash
cd apps/api
go build ./... && go vet ./... && go test ./...
```

And against the database you actually deploy to, which is where timestamp
precision and JSONB behaviour differ from SQLite:

```bash
docker compose up -d postgres
GRIT_TEST_DATABASE_URL=postgres://grit:grit@localhost:5434/grit go test ./...
```
