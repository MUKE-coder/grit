Step three · the part only you know

A billing cycle belongs to a recurring project and means nothing on a one-off one. That is a rule about the business, and it goes in the two places that exist for it.

// resources/projects/projects.ts — the form, for the person
{ key: "cycle", label: "Billing cycle", type: "select", options: [...],
  visibleWhen:  (v) => v.kind === "recurring",
  requiredWhen: (v) => v.kind === "recurring" }

// internal/services/project.go — the rule, for every caller
if p.Kind == "recurring" && p.Cycle == "" {
    return respond.Invalid("cycle", "a recurring project needs one")
}

gritframework.dev

This is the most honest slide in the demo, so do not rush it. The generator gives you the field. It cannot know that one field only applies when another holds a particular value, because that is domain knowledge, not schema. Two places, and they are different jobs. The form stops asking a question that does not apply, and a cycle left behind by a project that used to be recurring is cleared rather than kept. The service refuses it for every caller: the API, the CSV import, a job, a script. Doing only the first one is how bad data arrives through an import. Worth saying out loud: this landed in the framework because building this demo found it missing. That is the whole feedback loop, in one field.
